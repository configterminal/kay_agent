# 02-04 深入思考 long context加持的大模型企业还需要RAG

[0:00] 最近大语言模型的一个热门方向是支持超长的上下纹,
[0:05] 我们可以从下面这张图来看一下当前主流的大语言模型支持的上下纹的长度,
[0:13] 比如说拉玛,拉玛2,它可以支持4K的上下纹,
[0:19] 但是通过外推等一些技术,它可以支持超过32K的上下纹,
[0:26] 像Code3跟Gmini 1.5,它可以支持100万的一个Token的一个数录,
[0:33] 因此就能提出一个疑问,在如此长的上下纹的情况下,还需不需要RAG?
[0:42] 在这一小节,我们来对这个争议做一下说明,
[0:46] 首先我们来感受一下超长上下纹到底有多长,
[0:50] 像月之暗面的KimiChat它宣传能够支持200万的一个Token的数录,
[0:57] 那200万Token到底是一个什么概念呢?
[1:00] 做个简单的犯算,200万Token就相当于我们四大名著里面的鸿龙梦有四本鸿龙梦,
[1:08] 也就是说超长的上下纹窗口已经足够把几百上千个文档一股脑的塞入到大语言模型的一个对话窗口里面去,
[1:20] 我们知道RAG是利用铁知识库检索来辅助大语言模型来生成更准确的信息的一个手段,
[1:29] 那既然几百上千个文档都可以直接的放入到大语言模型,
[1:35] 那还有没有必要这样的一个外部的一个知识库作为外话呢?
[1:41] 我们来做一个详细的分析,
[1:45] 也就是说如果把铁知识作为上下纹直接输入到大语言模型而不需要RAG这个技术,这个方案是不是可行的?
[1:56] 首先,第一个问题就是推理成本比较高,效率比较低下,
[2:02] 我们知道输入越长,它占用的GPU资源的时间就越长,推理的速度就越慢,
[2:10] 另外一个是由于大语言模型本身并没有存储记忆的功能,
[2:15] 每次提问都需要附上几百个文档,
[2:20] 如果说使用API的话,就是使用那些收费的API接口,
[2:26] 那消耗的Token的数量相当是非常巨大的,也就是相当每次提问都要付出高顽的成本。
[2:35] 第二个问题是关于企业事有数据的安全性问题,
[2:39] 如果我们使用的大模型是外部其他公司的产品,
[2:43] 那么如果直接把文档输入到大模型,
[2:47] 就会直接暴露完整的我们企业的内部的事有数据,
[2:53] 这对于企业来说是一个比较大的一个三页风险。
[2:58] 第三个问题是大语言模型在处理超长上限纹的时候,
[3:02] 它的能力其实并不是完美的,还是有提升的空间的。
[3:07] 有人专门设计了一个叫做大海捞针的一个实验,
[3:11] 在这个实验中我们在一个超长的一个上下纹的水际的位置里面插入多个的针,
[3:19] 这个针其实就是对于我们有价值的一个知识点,
[3:23] 然后去验证大语言模型在这个超长上下纹中能否精准的检索出这些针,
[3:32] 也就是说能否精准的检索出对我们有价值的一个知识点。
[3:38] 举个例子就是说,
[3:39] 如果你想制作一个完美的一个披萨,
[3:42] 它有三个的秘密成分,
[3:45] 我们把这三个的秘密成分或者说这三个知识点随机的放在一个鸿鸣梦的一个故事里面去,
[3:53] 然后去问大语言模型制作完美披萨的一个秘密成分有哪些,
[3:59] 然后看一下大语言模型能否正确回答,
[4:03] 在左边这张图里面,
[4:05] 绿色的部分其实就是大语言模型能够正确回答的一个部分,
[4:11] 那其他颜色就是大语言模型在这方面做得不好的地方。
[4:15] 我们再来看一下GPD4在这个实验中的一个表现,
[4:21] 左边这张图是从真的数量也就是知识点的数量的角度来说明,
[4:27] 我们可以看到如果只有一个知识点,
[4:31] GPD4在检索跟推理都可以做得很好,
[4:36] 但是随着真的数量的增加,
[4:38] 比如说从增加到10个,
[4:40] 那GPD4在检索跟推理的准确率就会下降。
[4:45] 右边这张图是从上下文的长度来说明,
[4:50] 比如说上下文从1000增加到12万,
[4:55] 我们可以看到GPD4在1000的上下文中,
[5:00] 它的表现是很好的,
[5:02] 就是可以轻而易举地找到10个的知识点或者10个帧,
[5:08] 但是随着上下文的增加,
[5:11] 比如说增加到4万8还有增加到12万,
[5:16] 很明显就可以看到GPD4有很多帧它是丢失了或者说检索不到的,
[5:23] 就是上面这张图里面的一个红色的部分。
[5:27] 另外一个有趣的发现就是说GPD4在检索的时候,
[5:31] 其实是跟这个知识点或者真的位置是有关系的,
[5:36] 比如说虽然上下文从1000到12万,
[5:40] 但是其实越靠近后面的,
[5:44] 比如说知识点6到10,
[5:48] 这些它GPD4其实还是能够检索出来的,
[5:52] 但是对于上下文中比较靠前的知识点,
[5:55] 比如说1到5,
[5:58] 随着上下文的增加,
[6:02] 它其实检索GPD4表现就不是很好,
[6:06] 这也是一个比较有趣的地方,
[6:08] 也就是说它其实GPD4的检索能力其实是跟这些真的位置是有关系的。
[6:14] 通过上面的分析我们可以得出结论,
[6:18] 虽然大远模型拥有残上下文的一个能力,
[6:21] 但是还是有许多缺点的,
[6:24] 因此IG还是有很多应用场景的。

# 开发工作流

> 最后更新：2026-07-27

## 总览

```
① 需求讨论 ──→ ② 方案设计 ──→ ③ 接口定义 ──→ ④ 编码+评审循环 ──→ ⑤ 最终审查 ──→ ⑥ 同步文档 ──→ ⑦ 提交
                     │              │              │                   │
                  你审核         你确认        循环自驱            你验收
```

## 各阶段详解

### ① 需求讨论

- 你提想法，我分析可行性
- 可能触发调研（WebSearch）了解业界方案
- 输出：需求理解对齐，进入方案阶段

### ② 方案设计

- 我出设计文档，放到 `docs/architecture/` 下
- 内容包括：问题描述、方案架构、关键设计决策、改动范围、验证方案
- **必须等你审核通过**才进入下一步

### ③ 接口定义

- 前后端通信协议：SSE 事件格式、API 字段、数据类型
- 如果只改后端（无前端联动），可跳过
- **必须等你确认**接口格式

### ④ 编码 + 评审循环

```
┌─────────────────────────────────────────┐
│  编码（前后端并行）                       │
│  各自写代码 + 自测 (playwright/curl等)   │
└───────────────┬─────────────────────────┘
                │
                ▼
┌─────────────────────────────────────────┐
│  评审（reviewer Agent）                  │
│  产出评审文档 docs/review/xxx-review.md  │
└───────────────┬─────────────────────────┘
                │
           ┌────▼────┐
           │ 有问题？ │
           └────┬────┘
       ❌ 有    │    ✅ 无
       │        │         │
       ▼        │    ┌────▼─────┐
   轮数 +1      │    │ 循环结束  │
       │        │    │ → ⑤      │
  ┌────▼────┐   │    └──────────┘
  │ > 4轮？  │   │
  └────┬────┘   │
  ❌ 是 │ ✅ 否 │
  ┌─────▼──┐ ┌──▼──────┐
  │你决策   │ │继续编码 │
  │A:继续  │ │(回编码) │
  │B:搁置  │ └─────────┘
  └──┬──┬──┘
   A │  │ B
   ┌─┘  └──────────┐
   │               │
   ▼               ▼
  继续            记入文档
  (回编码)        搁置
                  (循环结束)
```

**评审轮数由评审文档记录**，reviewer Agent 每次输出注明 `Round N`。

**轮数 >4 必须等你决策**：继续修还是搁置评级。

**编码启动策略**：

| 改动范围 | 策略 |
|---------|------|
| 只改后端（无前端联动） | 1 个后端 coder |
| 只改前端（接口不变） | 1 个前端 coder |
| 前后端都改 | 2 个 coder 并行 |

**评审启动策略**：

| 改动量 | 策略 |
|--------|------|
| ≤1 文件，≤20 行 | 我直接看，不拉 reviewer |
| 2-3 文件，20-100 行 | 1 个 reviewer |
| 4+ 文件 或 新增模块 | 1 个 reviewer + 你最终审查 |

### ⑤ 你最终审查

- 看代码 diff + 跑起来验证
- **通过才进入同步文档**，有问题回到 ④

### ⑥ 同步文档

| 文件 | 更新内容 |
|------|---------|
| `CLAUDE.md` 开发进度区 | 状态变更：`[x]` / `[ ]` |
| `docs/architecture/index.md` | 新增文档链接 |
| `docs/architecture/` 对应文档 | 标注实现状态 |
| `docs/tasks.md` | 功能级 P0/P1/P2，含评审搁置项 |

**文档更新时机**：代码合入后立即更新，不在编码前或编码中更新。

### ⑦ 提交

`/qc` — Conventional Commits 格式，推主分支。

## 文档体系

| 文档 | 位置 | 职责 | 存活时间 |
|------|------|------|---------|
| **方案文档** | `docs/architecture/` | 功能设计、架构决策 | 长期保留 |
| **评审文档** | `docs/review/` | 每轮评审发现 + 修复状态 + 轮数 | 功能交付后归档 |
| **任务文档** | `docs/tasks.md` | P0/P1/P2 功能级待办 | 持续更新 |
| **同步文档** | `CLAUDE.md` + `index.md` | 当前进度状态 | 持续更新 |

### 评审文档格式

```markdown
# {功能名} 评审记录

> 关联方案: docs/architecture/xxx.md
> 开始: YYYY-MM-DD | 当前轮: N | 状态: 进行中/通过/搁置

## Round 1 — YYYY-MM-DD

### 发现问题

| # | 级别 | 描述 | 归属 | 状态 |
|----|------|------|------|------|
| B1 | 阻塞 | ... | 后端 | ✅ 已修 |
| M1 | 严重 | ... | 前端 | ⏳ 待修 |

### 搁置项

（本轮无）

## Round 2 — YYYY-MM-DD

...
```

**问题级别**：
- **阻塞**：不修无法合入
- **严重**：影响功能正确性或用户体验
- **建议**：可改进但非必须

## 特殊规则

1. **阻塞问题必须修**才能结束循环
2. **严重问题默认修**，除非你明确说搁置
3. **建议问题记录到评审文档**，由你在最终审查时决定
4. **轮数 >4 必须打断**，让你决策：继续 → 回编码，或搁置 → 记 `tasks.md` 并评级 P0/P1/P2
5. 评审搁置项升入 `tasks.md` 时标注来源 `(review: xxx)`，区分于功能需求
